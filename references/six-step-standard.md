# Skill 六步生产规范（全文）

## 0. 核心定位

- **tool 是原子能力，skill 是上层封装的业务工作流。**
- 设计 skill 的目标：能力标准化、可复用、可落地、可评测。
- 核心链路：定边界 → 做路由 → 编 SOP → 配资源 → 做评测 → 稳迭代。

## 1. 界定场景，锁定边界

### 1.1 场景准入（四者缺一不封装）

| 条件 | 判断问题 |
|---|---|
| 重复高频 | 这个任务每周/每月会重复出现吗？ |
| 流程固定 | 步骤是否稳定，还是每次都要重新设计？ |
| 目标独立 | 能否独立定义输入、输出、合格线？ |
| 可闭环 | 不依赖人工中途拍板也能完成吗？ |

### 1.2 粒度

- **不做大而全**：一个 skill 不包揽多个独立业务，避免臃肿难维护。
- **不做碎而杂**：不拆得过细，避免 Agent 频繁路由、逻辑混乱。
- 判断法：如果两个任务可以独立上线、独立评测，就拆；如果必须共享同一套输入输出和边界，就合。

### 1.3 边界清单

必须写清“能做什么 / 绝对不做什么”。模糊边界就是模型乱执行的入口。模板：

```markdown
| 能做 | 不做 |
|---|---|
| ... | ... |
```

## 2. 配置元信息，完成路由设计

### 2.1 元信息四件套

| 字段 | 作用 |
|---|---|
| name | 唯一标识，短横线命名 |
| description | 一句话用途 + 触发词 + **不适用于** |
| 触发条件 | 用户会怎么表达这个需求 |
| 禁用场景 | 什么情况下绝不能调用 |

### 2.2 正反用例

- 正向用例 ≥10 条：应该触发/应该选中。
- 反向用例 ≥10 条：不应触发，或应被另一个 skill 接住。
- 目标：路由准确率 ≥95%，杜绝漏触发、误触发。

### 2.3 冲突处理

两个 skill 都能命中时，在 description 写“不适用于 X（走 Y）”，并明确优先级：用户显式指定 > router > 默认。

## 3. 梳理业务 SOP，撰写核心执行规则

SOP 必须包含五个模块：

| 模块 | 要写清什么 | 缺失的后果 |
|---|---|---|
| 目标与验收标准 | 最终交付物、覆盖范围、什么算合格 | 模型自由发挥 |
| 固定执行流程 | 分步顺序、每步输入输出 | 跳步、顺序乱 |
| 依赖 | 底层工具、接口、知识库、外部 skill | 缺依赖时硬编 |
| 呈现格式与话术 | 排版、话术、模板、命名 | 每次格式不同 |
| 异常兜底 | 异常清单、降级路径、停止条件 | 边界输入直接崩 |

注意「验收标准」和「呈现格式」不是一回事：前者管内容对不对/全不全，后者管长什么样/怎么说。

## 4. 配套资源，按状态设计

### 4.1 资源清单

- few-shot 示例：至少一个正例、一个反例。
- 业务参考资料：领域知识、术语表、版本口径。
- 标准输出模板：HTML/Markdown/JSON 骨架。
- 中间状态：`.skill-state/<task-slug>.md`，保存进度、决策、待确认，避免每轮重头执行。
- 权限：高风险操作二次确认（覆盖、删除、联网、安装、写目录外）。

### 4.2 状态文件字段

```markdown
# <task-slug>
- 输入：
- 当前步骤：
- 关键决策：
- 待确认：
- 产物路径：
```

## 5. 搭建评测体系

**无评测不上线。** 三个核心指标：

| 指标 | 定义 | 门槛 |
|---|---|---|
| 路由准确率 | 该调用时调用、不该调用时不调用 | ≥95% |
| 任务完成率 | 正常场景能完整闭环 | 100% |
| 抗幻觉稳定性 | 边界/异常输入不输出错误、不编造 | 100% |

配套：

- 专属测试集：正/反/异常三类。
- 评分表：每项权重与通过线。
- 回归集：只增不减；每次改规则必须重跑。
- 失败回流：`eval/failures.md` 四列「输入/期望/实际/修正」。

## 6. 灰度上线 + 持续迭代

- MVP 最小闭环先上线：先跑通核心能力，再优化细节。
- 版本号 + 更新日期：每次行为变化升版本。
- 灰度：新触发词/新规则先在小范围真实场景验证，再开放。
- 失败回流：线上失败 case 反向补规则、改 SOP、补回归用例。
- 迭代不降级：任何修改都要跑回归集。

## 7. 编辑质量门（防空话错位/命名撞车）

### 7.1 章节契约

| 章节 | 这一节回答的问题 | 只收 | 不收 |
|---|---|---|---|
| 开头 | 这是什么、为什么做 | 定义、定位、目标 | 操作步骤、实现细节 |
| 流程节 | 具体怎么做 | 动作、输入输出、依赖 | 定义、原理、选型辩论 |
| 评测节 | 怎么判断合格 | 指标、门槛、回归方法 | 定义、操作步骤 |
| 迭代节 | 上线后怎么改 | 动作、失败回流、灰度 | 定义、原理、背景 |

### 7.2 术语表 + MECE

| 术语/模块 | 管什么 | 不管什么 | 易混词 |
|---|---|---|---|
| 目标与验收标准 | 内容完整性、覆盖范围、合格线 | 排版、话术 | 输出格式 |
| 呈现格式与话术 | 排版、话术、模板、命名 | 内容是否正确 | 输出标准 |

MECE 测试：同一段内容能否同时放进两个模块？能 → 边界没写清，改名或补“不管什么”。

### 7.3 冷读者复审

只读标题和每块首句，回答：

1. 这句话在回答这个标题的问题吗？
2. 只看标题，能说出任意两节的区别吗？
3. 有没有两个标题共享同一个关键词？
4. 有没有一节最后一句在讲下一节的事？

输出 `句子/标题 | 现位置 | 应位置或改名建议`，清单清零才算通过。

## 8. 上线检查表

- [ ] 场景四条件成立；边界能一句话说清。
- [ ] frontmatter 有 name/description/触发/不适用/version/last_updated。
- [ ] SOP 五模块齐全；验收标准与呈现格式分工明确。
- [ ] 资源、状态、权限二次确认齐全。
- [ ] 正反用例各 ≥10；三指标有门槛。
- [ ] `eval/cases.md`、`eval/failures.md` 存在。
- [ ] 冷读者复审清单为空。
- [ ] 审计脚本 PASS。
